Yes. In fact, you can build a micro-SBERT equivalent entirely in JavaScript, without Python, without an external API, and potentially without even running a backend server.

There is one important distinction: we can reproduce much of SBERT's functionality, but building a genuinely semantic embedding model from scratch is different from implementing the SBERT inference process.

Given your document summarization and memory-management idea, I would approach this as a small, self-contained JavaScript semantic engine.

## 1. What functionality are we trying to replicate?

SBERT (Sentence-BERT) converts sentences or paragraphs into numerical vectors called embeddings.

For example:

| Text                                              | Expected semantic meaning |
| ------------------------------------------------- | ------------------------- |
| The insured reported a vehicle accident.          | Auto accident             |
| The policyholder filed a claim after a collision. | Auto accident             |
| The house suffered water damage.                  | Property damage           |
| Premium increased by 10%.                         | Policy pricing            |

SBERT can recognize that the first two sentences are semantically similar even though their words are different.

The basic process:

Input text

The policyholder filed a claim after a collision.

JavaScript text processing / embedding model

Numerical vector

[-0.12, 0.83, 0.21, 0.45, ...]

Cosine similarity

# 0.94

Illustrative similarity score

## 2. Three ways to develop it

There are three possible approaches.

| Approach                                    | JavaScript only? | Semantic accuracy   |
| ------------------------------------------- | ---------------- | ------------------- |
| TF-IDF + cosine similarity                  | Yes              | Low to moderate     |
| Custom micro-embedding model                | Yes              | Depends on training |
| Pretrained MiniLM/SBERT model running in JS | Yes              | Good                |

My recommendation is the third approach initially, followed by experimentation with a smaller custom model.

## 4. What I would build for your document summarization project

Consider your earlier example of a 10-page insurance claim document.

I would build five JavaScript modules:

## Micro Semantic Engine

1\. Document Processor

Extract text and divide it into paragraphs and page-level chunks.

2\. Embedding Generator

Convert every paragraph into a numerical vector.

3\. Semantic Index

Store vectors alongside page number, paragraph number and metadata.

4\. Similarity Search

Find relevant paragraphs using cosine similarity.

5\. Context Retrieval

Return relevant paragraphs with their original page references.

For example, a user asks:

"What was the cause of the accident?"

The engine searches all 10 pages and might identify:

- Page 2: Insured reported a collision.
- Page 4: Police report indicates another vehicle changed lanes.
- Page 7: Witness statement confirms the other vehicle's movement.
- Page 9: Adjuster concluded that the other driver was responsible.

This is where semantic search becomes useful.

## 5. Can we make it even smaller?

Yes. There is an interesting alternative worth exploring.

Instead of using a 22-million-parameter MiniLM model, we could develop a custom micro semantic engine with:

- A small domain-specific vocabulary.
- Word and phrase vectors.
- Synonym mappings.
- TF-IDF weighting.
- Sentence-level similarity.
- Domain-specific terminology for insurance claims.

This would be significantly smaller and could run entirely in JavaScript.

However, it would not automatically understand contextual meaning as well as SBERT. It would need carefully designed features and possibly domain-specific training.

## 6. My recommendation

I would build two interchangeable engines behind the same JavaScript interface:

| Capability             | Engine A                   | Engine B                          |
| ---------------------- | -------------------------- | --------------------------------- |
| Implementation         | Pure JavaScript algorithms | MiniLM running in JS              |
| Model weights          | None                       | Pretrained weights                |
| Semantic understanding | Limited                    | Stronger                          |
| Runtime                | Extremely lightweight      | More resource intensive           |
| Internet/API           | Not required               | Not required after model download |

Then test both against the same 10-page insurance claim document.

Measure:

1. Retrieval accuracy.
2. Memory consumption.
3. Processing time.
4. Model size.
5. Accuracy of page-level metadata.

The interesting engineering opportunity: You could eventually have a lightweight, browser-based semantic search engine that processes insurance documents, builds its own index, and retrieves relevant evidence without sending the documents to an external embedding API.

I would start by building the complete JavaScript prototype with interchangeable embedding engines, using your insurance claim document scenario 
as the test case.

That changes the architecture quite significantly. I think there is a very interesting product opportunity here.

You are not really trying to build a smaller SBERT for document processing. You are trying to build a browser-based AI/ML engineering challenge platform, where candidates demonstrate how effectively they use AI to solve problems.

The micro semantic model becomes one of the tools available to the candidate.

And your key constraint is important:

A candidate should be able to open a URL on their mobile phone, use the application in the browser, and complete an AI/ML challenge without installing Python, Node.js, or any other software.

I would design this as a zero-install, mobile-first application.

## 1. Proposed architecture

Candidate's mobile browser

Chrome / Safari — no installation

Mobile-first challenge application

- Problem statement
- Dataset / sample documents
- Interactive coding environment
- AI usage workspace
- Test cases and evaluation

JavaScript engine

Algorithms, semantic search, scoring

Micro AI model

Embeddings and inference

Results and assessment

Accuracy · Efficiency · AI reasoning · Quality · Validation

Core computation runs locally in the browser. An optional server can handle challenge administration and assessment submissions.

I would use:

- HTML5, CSS and JavaScript for the application.
- Web Workers for background processing.
- IndexedDB for local datasets and results.
- WebAssembly or WebGPU where supported for model inference.
- A lightweight quantized embedding model as an optional component.

The application can be hosted as a static website. A candidate simply opens a link.

## 2. What should the micro model actually do?

I would avoid trying to build a general-purpose miniature ChatGPT. That is unnecessary for your objective.

Instead, build a small collection of AI/ML capabilities:

| Capability          | Example challenge                             |
| ------------------- | --------------------------------------------- |
| Semantic similarity | Identify similar insurance claim descriptions |
| Text classification | Classify claims into loss categories          |
| Entity extraction   | Identify insured, policy number, loss date    |
| Semantic retrieval  | Find relevant paragraphs across 10 pages      |
| Clustering          | Group similar claims                          |
| Anomaly detection   | Identify unusual claim patterns               |
| Summarization       | Produce a structured claim summary            |

These are excellent interview challenges because candidates must decide which AI technique is appropriate.

For example, a candidate who uses an LLM to solve a simple classification problem involving five fixed categories might be making a poor engineering decision.

Someone who recognizes that deterministic rules or TF-IDF are sufficient may demonstrate better engineering judgment.

## 3. The important part: assess the candidate's AI mindset

I would not assess candidates simply on whether they produce the correct answer.

I would assess how they approach the problem.

## AI engineering assessment framework

# 01

Problem decomposition

Did the candidate understand and break down the problem?

# 02

AI tool selection

Did they select an appropriate model or deterministic approach?

# 03

AI utilization

Did they use AI effectively, with good prompts and iterative refinement?

# 04

Engineering efficiency

Did they minimize unnecessary computation, tokens, memory and complexity?

# 05

Quality and validation

Did they test edge cases, measure accuracy and detect hallucinations?

# 06

Production mindset

Did they consider scalability, maintainability, security and monitoring?

This is a much more meaningful assessment than asking someone to write Python code to train a model.

## 5. Important mobile design considerations

There are a few constraints I would design around from day one.

| Area               | Recommendation                                        |
| ------------------ | ----------------------------------------------------- |
| Application size   | Keep initial download very small                      |
| Model              | Optional quantized model, downloaded only when needed |
| Offline capability | PWA with cached challenges                            |
| Processing         | Browser CPU first, WebGPU where available             |
| UI                 | Single-column, touch-friendly                         |
| Coding             | Lightweight editor such as CodeMirror                 |
| Data               | Small datasets, typically 100–1,000 records           |

One important point: running a 20-million-parameter model on a phone is possible, but performance varies considerably by device. We should benchmark on actual Android and iPhone browsers rather than assume every phone can run it comfortably.

Also, I would not force candidates to write extensive code on a phone. Some challenges can assess architecture, prompt engineering, model selection, data reasoning and testing through interactive interfaces.
